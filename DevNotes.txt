The case for JSON
-----------------

JSON is the natural fit for this application for several reasons that align directly with the design goals established throughout this conversation.

PWA compatibility — the frontend is a PWA running in a browser. 
The browser's fetch API speaks JSON natively. 
A binary protocol would require custom serialization and deserialization code in JavaScript on the client side, adding complexity to the frontend that vanilla JS was specifically chosen to avoid.

Human readability — during development and testing, being able to read API responses directly in the browser or in curl output is valuable. 
The Crow routes already written in this conversation all produce JSON. A binary protocol makes debugging significantly harder.

Traffic volume is bounded — the rate limiting established earlier means the event rate is inherently low. 
One event per player per game per hour across your projected user base produces a modest request volume that JSON handles comfortably. 
The overhead of JSON serialization will never be a measurable bottleneck at this scale.

Crow support — nlohmann/json is already part of the planned stack. JSON responses from Crow are straightforward and well understood.

A middle path worth considering
-------------------------------

Rather than choosing between pure JSON and a binary protocol, the more relevant scalability question for ToY is payload efficiency within JSON. 
A few simple conventions keep the JSON responses lean without introducing binary complexity:

// Verbose — wastes bandwidth on field names repeated in every response
{
    "eventIdentifier": 42,
    "gameIdentifier": 7,
    "playerIdentifier": 3,
    "eventTimestamp": 1000000,
    "matchedEventIdentifier": 41,
    "eventStatus": 1
}

// Lean — short field names, same information
{
    "id": 42,
    "gid": 7,
    "uid": 3,
    "ts": 1000000,
    "mid": 41,
    "st": 1
}

For a PWA the JavaScript client knows what the fields mean from the API contract. 
Short field names reduce payload size without any binary parsing complexity on either end.

Recommendation
--------------

JSON throughout, with lean field names in the response bodies. 
It is consistent with the single binary, low complexity philosophy that has guided every other decision in this project, it requires no additional client-side infrastructure, and it leaves the binary option available as a targeted optimization for specific high-volume endpoints if that need ever arises. 
The scalability of this application will be determined by the backend data structures and the hosting infrastructure long before JSON serialization becomes a concern.

Cross Platform Memory Mapped Files
----------------------------------

#include <iostream>
#include <string>
#include <string_view>

#ifdef _WIN32
    #include <windows.h>
#else
    #include <fcntl.h>
    #include <sys/mman.h>
    #include <sys/stat.h>
    #include <unistd.h>
#endif

class CrossPlatformMmap {
public:
    CrossPlatformMmap(const std::string& filepath, size_t size) : size_(size) {
#ifdef _WIN32
        // 1. Open or create the file on Windows
        file_handle_ = CreateFileA(filepath.c_str(), GENERIC_READ | GENERIC_WRITE, 
                                   0, NULL, CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);
        if (file_handle_ == INVALID_HANDLE_VALUE) return;

        // 2. Create the file mapping object
        mapping_handle_ = CreateFileMappingA(file_handle_, NULL, PAGE_READWRITE, 
                                             0, static_cast<DWORD>(size_), NULL);
        if (!mapping_handle_) {
            CloseHandle(file_handle_);
            return;
        }

        // 3. Map the view into the process virtual address space
        data_ = static_cast<char*>(MapViewOfFile(mapping_handle_, FILE_MAP_ALL_ACCESS, 0, 0, size_));
#else
        // 1. Open or create the file on Linux
        fd_ = open(filepath.c_str(), O_RDWR | O_CREAT | O_TRUNC, S_IRUSR | S_IWUSR);
        if (fd_ == -1) return;

        // 2. Memory mapping requires the file on disk to physically match the requested size
        if (ftruncate(fd_, size_) == -1) {
            close(fd_);
            return;
        }

        // 3. Map the file using POSIX mmap
        data_ = static_cast<char*>(mmap(NULL, size_, PROT_READ | PROT_WRITE, MAP_SHARED, fd_, 0));
        if (data_ == MAP_FAILED) {
            data_ = nullptr;
            close(fd_);
        }
#endif
    }

    ~CrossPlatformMmap() {
        if (!data_) return;
#ifdef _WIN32
        UnmapViewOfFile(data_);
        CloseHandle(mapping_handle_);
        CloseHandle(file_handle_);
#else
        munmap(data_, size_);
        close(fd_);
#endif
    }

    // Get pointer to the memory region
    char* data() const { return data_; }
    bool is_valid() const { return data_ != nullptr; }

private:
    size_t size_ = 0;
    char* data_ = nullptr;

#ifdef _WIN32
    HANDLE file_handle_ = INVALID_HANDLE_VALUE;
    HANDLE mapping_handle_ = NULL;
#else
    int fd_ = -1;
#endif
};

int main() {
    std::string filename = "shared_buffer.dat";
    size_t mapping_size = 4096; // 4 KB

    CrossPlatformMmap mmap_file(filename, mapping_size);

    if (!mmap_file.is_valid()) {
        std::cerr << "Failed to map file!" << std::endl;
        return 1;
    }

    // Write cross-compatible data via pointer
    char* ptr = mmap_file.data();
    std::string_view message = "Hello from cross-platform memory mapping!";
    std::copy(message.begin(), message.end(), ptr);

    std::cout << "Successfully wrote to mapped memory: " << ptr << std::endl;
    return 0;
}

Crucial Platform Differences to Keep in Mind

If you are writing the implementation wrapper yourself, ensure you account for these architectural nuances:

- File Sizing: 
  On Linux (mmap), you must call ftruncate or physically expand the file to your desired size before calling mmap. 
  Windows handles the file sizing directly within CreateFileMapping via its sizing arguments.
  
- Error Handling: 
  Linux emits severe signals (SIGBUS/SIGSEGV) if you attempt to access memory beyond the physical end of the file. 
  Windows throws normal structured exceptions or API errors
  
- Alignment: 
  Memory mapping requires your mapping offsets to align cleanly with the operating system's internal virtual memory page boundaries (usually 4KB or 64KB chunks).

#include <iostream>
#include <string>

// Platform detection and header inclusion
#if defined(_WIN32) || defined(_WIN64)
    #define PLATFORM_WINDOWS
    #define WIN32_LEAN_AND_MEAN
    #include <windows.h>
#elif defined(__linux__) || defined(__unix__)
    #define PLATFORM_LINUX
    #include <fcntl.h>
    #include <sys/mman.h>
    #include <sys/stat.h>
    #include <unistd.h>
#else
    #error "Unsupported Operating System"
#endif

class MemoryMappedFile {
private:
    void* m_data = nullptr;
    size_t m_size = 0;

#if defined(PLATFORM_WINDOWS)
    HANDLE m_fileHandle = INVALID_HANDLE_VALUE;
    HANDLE m_mappingHandle = NULL;
#elif defined(PLATFORM_LINUX)
    int m_fileDescriptor = -1;
#endif

public:
    MemoryMappedFile(const std::string& filepath, size_t size) : m_size(size) {
        if (size == 0) throw std::invalid_argument("Size must be greater than 0");

#if defined(PLATFORM_WINDOWS)
        // 1. Open or create the file
        m_fileHandle = CreateFileA(filepath.c_str(), GENERIC_READ | GENERIC_WRITE, 
                                   FILE_SHARE_READ | FILE_SHARE_WRITE, NULL, 
                                   OPEN_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);
        if (m_fileHandle == INVALID_HANDLE_VALUE) {
            throw std::runtime_error("Windows: Failed to open/create file.");
        }

        // 2. Create the file mapping object
        m_mappingHandle = CreateFileMappingA(m_fileHandle, NULL, PAGE_READWRITE, 
                                             0, static_cast<DWORD>(m_size), NULL);
        if (m_mappingHandle == NULL) {
            CloseHandle(m_fileHandle);
            throw std::runtime_error("Windows: Failed to create file mapping object.");
        }

        // 3. Map the view of the file into memory
        m_data = MapViewOfFile(m_mappingHandle, FILE_MAP_ALL_ACCESS, 0, 0, m_size);
        if (!m_data) {
            CloseHandle(m_mappingHandle);
            CloseHandle(m_fileHandle);
            throw std::runtime_error("Windows: Failed to map view of file.");
        }

#elif defined(PLATFORM_LINUX)
        // 1. Open or create the file with read/write permissions
        m_fileDescriptor = open(filepath.c_str(), O_RDWR | O_CREAT, S_IRUSR | S_IWUSR);
        if (m_fileDescriptor == -1) {
            throw std::runtime_error("Linux: Failed to open/create file.");
        }

        // 2. Truncate/extend the file to the target size 
        if (ftruncate(m_fileDescriptor, m_size) == -1) {
            close(m_fileDescriptor);
            throw std::runtime_error("Linux: Failed to resize file.");
        }

        // 3. Map the file into memory
        m_data = mmap(NULL, m_size, PROT_READ | PROT_WRITE, MAP_SHARED, m_fileDescriptor, 0);
        if (m_data == MAP_FAILED) {
            close(m_fileDescriptor);
            m_data = nullptr;
            throw std::runtime_error("Linux: Failed to map memory.");
        }
#endif
    }

    ~MemoryMappedFile() {
        if (!m_data) return;

#if defined(PLATFORM_WINDOWS)
        UnmapViewOfFile(m_data);
        CloseHandle(m_mappingHandle);
        CloseHandle(m_fileHandle);
#elif defined(PLATFORM_LINUX)
        munmap(m_data, m_size);
        close(m_fileDescriptor);
#endif
    }

    // Disable copy constructors to ensure clean RAII memory management
    MemoryMappedFile(const MemoryMappedFile&) = delete;
    MemoryMappedFile& operator=(const MemoryMappedFile&) = delete;

    // Direct pointer to the memory space
    void* data() const { return m_data; }
    size_t size() const { return m_size; }
};

int main() {

        // Write data directly to memory

    } catch (const std::exception& e) {
        std::cerr << "Error: " << e.what() << std::endl;
    }

}

Running Node tests on Ubuntu server:
------------------------------------

To run both a C++ executable and a Node.js unit test sequentially or concurrently in a single SSH session, 
you must manage the terminal processes so the C++ background task does not block your test execution.

Method 1: Background Operator (&) and wait-on (Recommended)

This is the cleanest approach for automated scripts or CI/CD pipelines. 
It launches the C++ app in the background, waits for its port/process to become active, runs the tests, and cleans up.

- Install the wait-on utility to ensure your tests do not start before the C++ app is fully ready:
  npm install --save-dev wait-on
- Run the C++ executable in the background using &, wait for it, run tests, and kill the process afterward:bash
  ./my_cpp_executable & CPP_PID=$! && npx wait-on tcp:8088 && npm test; kill $CPP_PID

Replace 8080 with the actual port your C++ application listens on.
kill $CPP_PID ensures the C++ app terminates cleanly after the tests finish or fail.

Method 2: Terminal Multiplexing with tmux (Best for Manual Debugging)

If you need to watch the live logs of your C++ executable while simultaneously interacting with your Node.js unit tests, use tmux. 
It splits your single SSH terminal window into multiple panels.

- Start a new tmux session:
  tmux new -s my-test-session
- Run your C++ executable in the active window:
  ./my_cpp_executable
- Split the screen horizontally by pressing Ctrl + B, then release and press % (or " for a vertical split).
- In the new pane, run your Node.js tests:
  npm test
- To exit and close everything when finished, type exit in each pane.

Method 3: Handle Life Cycle Directly Inside Node.js (Most Robust) 

Instead of handling this via shell scripting, you can program Node.js to spin up and tear down the C++ executable automatically during the test lifecycle using child_process.
If you use a framework like Jest or Mocha, add this to your global setup and teardown configurations:

Global Setup Script (setup.js):

	const { spawn } = require('child_process');

	module.exports = async () => {
	  // Start the C++ executable
	  global.__CPP_PROCESS__ = spawn('./my_cpp_executable', [], {
		stdio: 'inherit' // Forwards C++ stdout/stderr to your terminal
	  });
	  
	  // Give the C++ app 2 seconds to initialize before tests start
	  await new Promise(resolve => setTimeout(resolve, 2000));
	};

Global Teardown Script (teardown.js):

	module.exports = async () => {
	  // Cleanly kill the C++ app after tests finish
	  if (global.__CPP_PROCESS__) {
		global.__CPP_PROCESS__.kill();
	  }
	};

Native Node Test Runner:
------------------------

To automate this using Node's native test runner (node --test), you can use a global hook script. 
Node's native runner supports a --test-reporter or an entry file architecture, 
but the cleanest way to wrap the entire test suite lifecycle without modifying every single file 
is to use a custom master script or Node's pre-load capabilities.

Here is how to set up the automatic lifecycle directly in your project.

Step 1: Create a Master Test Runner (run-tests.js)

Create a file named run-tests.js in your project root. This script will launch your C++ binary, wait for it to boot,
invoke Node's native test runner, and ensure the C++ binary is killed even if tests fail.

	const { spawn } = require('child_process');

	// 1. Start the C++ executable in the background
	const cppProcess = spawn('./my_cpp_executable', [], {
	  stdio: 'inherit' // Forwards C++ stdout/stderr to your terminal
	});

	// Helper to clean up the C++ process safely
	function cleanup() {
	  if (cppProcess && !cppProcess.killed) {
		console.log('\nStopping C++ executable...');
		cppProcess.kill('SIGTERM');
	  }
	}

	// Ensure cleanup runs if the main script gets interrupted (Ctrl+C)
	process.on('SIGINT', () => { cleanup(); process.exit(1); });
	process.on('SIGTERM', () => { cleanup(); process.exit(1); });

	// 2. Wait for the C++ application to initialize
	// (Adjust the timeout or use a TCP socket check if it takes longer)
	setTimeout(() => {
	  console.log('C++ executable ready. Starting Node.js native tests...');

	  // 3. Spawn Node's native test runner
	  // This looks for all files matching test patterns (e.g., *.test.js)
	  const testProcess = spawn('node', ['--test'], { stdio: 'inherit' });

	  // 4. Handle test process completion
	  testProcess.on('close', (code) => {
		cleanup();
		process.exit(code); // Exit with the same code as the tests (0 for success)
	  });
	}, 2000); // 2-second delay for C++ startup

Step 2: Update Your package.json

Update the test script in your package.json file to point to your new master runner instead of invoking node --test directly:

	{
	  "scripts": {
		"test": "node run-tests.js"
	  }
	}

Step 3: Run Your Tests

Now, you can execute your entire test pipeline in your single SSH terminal connection using your standard test command:

	npm test

Alternative: Keep C++ Application Separated in Bash

If you prefer not to write JavaScript wrapper code, you can use Node's native test command directly in your shell script. 
Ensure you trap terminal exits to prevent the C++ app from becoming a "zombie" process if the tests crash:

	# Start C++ app, wait 2 seconds, run native tests, and ensure cleanup happens
	./my_cpp_executable & CPP_PID=$! && sleep 2 && node --test; EXIT_CODE=$?; kill $CPP_PID; exit $EXIT_CODE

Permissions:

server.crt — not sensitive; it's the public half of the pair, meant to be presented to anyone who connects.

    chmod 644 /etc/toy/certs/server.crt

server.key — this is the one that actually matters. Compromise of this file lets someone impersonate your server entirely.

    chmod 600 /etc/toy/private/server.key
    chown eng:eng /etc/toy/private/server.key

600 = owner read/write only, nobody else on the system can read it — including other unprivileged users, if this box is ever shared or compromised at a lower level.
Directory permissions matter too, not just the file — a 600 file inside a world-listable/readable directory is less protected than it looks, since directory permissions govern whether the file can even be found/traversed to in the first place:

    chmod 700 /etc/toy/private
    chmod 755 /etc/toy/certs

700 on private/ means only the owner (eng) can list, enter, or access anything inside it at all — certs/ can stay more open (755) since nothing inside it is sensitive.

Logging:
--------

On modern Ubuntu systems, systemd automatically captures everything written to stdout (standard output) 
and stderr (standard error) by a daemon and routes it directly to the system journal (journald).

This is a core tenet of modern "Cloud Native" and Twelve-Factor App design patterns: 
applications should treat logs as event streams and simply write them unbuffered to the console.

When you configure your Crow app to run as a background service, you will create a systemd service unit file (e.g., /etc/systemd/system/myapp.service).
By default, systemd takes care of the capture. Your service file can be as simple as this:

    [Unit]
    Description=Crow PWA Application
    After=network.target

    [Service]
    Type=simple
    ExecStart=/usr/local/bin/myapp
    Restart=on-failure
    User=myappuser

    # Optional: Tags your logs in the journal
    SyslogIdentifier=myapp

    [Install]
    WantedBy=multi-user.target

How to Read the Captured Logs:

Tail logs in real-time (like tail -f):
    journalctl -u myapp.service -f

View logs from today only:
    journalctl -u myapp.service --since today

Filter to show only errors (stderr entries):
    journalctl -u myapp.service -p err

Key Advantages of Relying on stdout/stderr:

1. Automatic Log Rotation: journald manages log sizes natively. It will automatically compress logs and rotate them out when they reach a certain disk percentage, preventing your server from running out of space.
2. Standardized Formatting: Systemd automatically prepends timestamps and the service name to every single line your app outputs.
3. No File Permission Headaches: Your Crow app doesn't need write permissions to /var/log/ or a custom log directory. It just writes to its own console stream, increasing security.
4. Centralized Log Management: All logs from different services are aggregated in one place, making it easier to monitor and analyze system behavior.
5. Integration with Monitoring Tools: Many modern monitoring and alerting tools (like Prometheus, Grafana, or ELK stack) can directly ingest logs from journald, enabling real-time observability.
6. Simplified Deployment: By writing logs to stdout/stderr, you avoid the complexity of managing separate log files, permissions, and rotation policies.
7. Consistency Across Environments: Whether you're running your app in development, staging, or production, the logging behavior remains consistent, reducing surprises when moving between environments.
8. Easy Debugging: When debugging issues, you can quickly access the logs without needing to SSH into the server and navigate to log directories.
9. Reduced Disk I/O: Writing to stdout/stderr is generally more efficient than writing to disk, especially when journald is configured to store logs in memory or a fast storage medium.
10. Future-Proofing: As your application scales or moves to containerized environments (like Docker or Kubernetes), relying on stdout/stderr aligns with best practices for cloud-native applications.

Because C++ standard output (std::cout) is buffered by default when not running in an interactive terminal, logs might not appear in journalctl immediately.
To fix this and get real-time log capturing, ensure you flush the stream or use std::endl instead of \n, or disable buffering entirely at the start of your main() function:

    #include <iostream>

    int main() {
        // Disable stdout buffering so logs stream instantly to systemd
        std::setvbuf(stdout, NULL, _IONBF, 0); 
    
        // Your Crow application code...
    }

Server Optimization Summary:
============================
NOTE: CONFIRM WITH CLAUDE BEFORE MAKING ANY CHANGES TO THE SERVER

Key Performance Tuning Vectors:
-------------------------------

Since your objective is simulating a real workload on this mobile workstation, here are three high-value areas to tune that will impact your specific architecture far more than any display configurations:

1. Swap Aggressiveness (vm.swappiness)

Because your database relies on memory-mapped files, Linux might try to aggressively swap out anonymous memory (like your std::unordered_map indexes) to make room for file-backed page caches.

- To prevent your indexes from dropping to disk, force Linux to favor keeping anonymous memory in RAM:sudo sysctl vm.swappiness=10

2. Maximum Memory Map Mappings

By default, the Linux kernel limits a single process to 65,530 memory mappings (vm.max_map_count).

If your game simulation scales up and opens numerous fixed-size array segments concurrently, your CROW server could crash with an Out-of-Memory or bad allocation error.
- Check your limit: cat /proc/sys/vm/max_map_count
- If needed, double or triple it by appending vm.max_map_count=262144 to /etc/sysctl.conf.

3. Consider an Alternate Allocator for std::unordered_map

The default glibc allocator (ptmalloc) can cause severe memory fragmentation when an std::unordered_map grows, shrinks, or rehashes. 
If you notice your memory footprint creeping up unnaturally during simulation:

- Link your CROW application against jemalloc or TCMalloc. These modern allocators manage small node allocations much more efficiently and will provide a much truer simulation of a production-grade in-memory database wrapper.

Configuring Huge Pages for std::unordered_map
---------------------------------------------

By default, the Linux kernel manages memory in tiny 4KB chunks (pages). 
Because an std::unordered_map creates thousands of small node allocations scattered across RAM, the CPU has to constantly look up page mappings in its Translation Lookaside Buffer (TLB), causing "TLB misses" that slow down lookups.

By enabling Huge Pages (usually 2MB), you reduce the sheer number of page entries the CPU has to track by a factor of 500, significantly speeding up random memory access.

Step 1: Check Your CPU's Default Huge Page Size

Run this command to see what size Huge Pages your system supports and if any are already active:

  grep Huge /proc/meminfo

- Look at Hugepagesize:. On x86_64 systems, it will almost always say 2048 kB (2MB).

- Take note of HugePages_Total: 0, which means none are allocated yet.

Step 2: Calculate How Many Pages to Allocate

Since Huge Pages must be locked into physical RAM and cannot be swapped out, you need to dedicate a specific portion of your RAM to them.

- Example: If you want to reserve 4GB of RAM for your application's memory pool, and your page size is 2MB: 4096 MB / 2 MB = 2048 Huge Pages.

Step 3: Allocate the Huge Pages Dynamically (Temporary Test)

Before making changes permanent, test the allocation on your running server:

  sudo sysctl -w vm.nr_hugepages=2048

Run grep Huge /proc/meminfo again. You should now see HugePages_Total: 2048 and HugePages_Free: 2048.

Step 4: Make the Allocation Permanent

If your game simulation runs smoothly with the allocation, ensure the settings persist across system reboots:

1. Open the sysctl configuration file:

  sudo nano /etc/sysctl.conf

2. Add this line to the very bottom of the file:

  vm.nr_hugepages=2048

3. Save and exit (Ctrl+O, Enter, Ctrl+X).
  
Step 5: Informing Your C++ Application

Standard C++ allocations (new or malloc) do not automatically use Huge Pages. 
To make your std::unordered_map utilize them, you have two primary options:

- Option A (Transparent Huge Pages - Easiest): 

  You can tell the Linux kernel to automatically merge standard 4KB pages into Huge Pages in the background when it notices large contiguous memory blocks.
  Ensure it is enabled system-wide by running:

  echo always | sudo tee /sys/kernel/mm/transparent_hugepage/enabled

- Option B (Custom C++ Allocator - Best Performance): 

  For maximum control, pass a custom allocator to your std::unordered_map declaration that uses mmap with the MAP_HUGETLB flag to explicitly request the pre-allocated huge page blocks you configured in Step 3.

Why This Profile Is Perfect for Your Architecture
-------------------------------------------------

- Massive Indexing Ceiling: 
  The default std::unordered_map in C++ has an overhead of roughly 24 to 32 bytes per node (excluding your actual game struct data) just to handle bucket pointers. 
  With 17.5GB free, your system can easily maintain tens of millions of active index nodes simultaneously without breaking a sweat.

- Maximum OS Page Cache Acceleration: 
  Since your dataset uses memory-mapped files (mmap), the Linux kernel will seamlessly consume your unused RAM to cache those files directly into physical memory (buff/cache). 
  This means your disk-backed files will read and write at raw RAM speeds (nanoseconds instead of milliseconds), effectively turning your file storage into a high-performance in-memory database.

Two Critical Reminders for Your 18GB Layout

Because you plan to test Huge Pages on this specific hardware configuration, keep these two system traits in mind:

1. Do Not Over-Allocate Your Huge Pages: Huge Pages permanently lock a chunk of physical memory away from the operating system. 
   If you allocate a 12GB Huge Page pool (vm.nr_hugepages=6144), your available system RAM instantly drops to 6GB. 
   Ensure you leave at least 2GB entirely unallocated for standard OS functions, network buffers, and your CROW web server's core stack.

2. Watch for Fragmentation During Allocation: 
   Because this server is a mobile workstation, its memory controller might handle physical memory routing across non-contiguous layouts. 
   If you try to allocate a large number of Huge Pages after the server has been running for days, the command might fail because it cannot find enough continuous chunks of raw memory. 
   Always allocate your Huge Pages immediately after a clean boot.
   
   
Tuning CROW Application
-----------------------

Tune CROW's concurrency model, minimize dynamic allocations in handlers and enforce system-level resource caps via cgroups or systemd-analyze

App-Level Tuning:
- Limit Concurrency: Reduce the number of worker threads
- Reuse Objects: Pre-allocate JSON responses or use object pools rather than instantiating new crow::json::wvalue on every request
- Avoid String Copying: Pass request bodies and strings by const reference inside lambda handlers to reduce memory churn

Server-Level Config:

- Systemd Memory Limits: Add MemoryMax=512M or MemoryHigh=400M to your applications systemd service file to safely contain memory spikes and prevent kernel OOM cascades
- Lower swappiness: Reduce kernel aggressiveness in swapping memory by setting vm.swappiness = 10 in /etc/sysctl.conf
